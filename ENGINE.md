# ENGINE.md

Compagno di [AGENTS.md](AGENTS.md): quello raccoglie le ricette, questo è la mappa dell'implementazione interna dell'Engine che i README non citano per nome. `backend/README.md` e `frontend/README.md` documentano la superficie consumabile, cioè cosa inietti, estendi, configuri; qui stanno i file che quella superficie la implementano, attrezzeria interna, mai un seam. Lo scopo non è invitarti a modificarli (l'Engine resta INTOCCABILE, la regola d'oro non cambia), ma farti trovare "dov'è" e "perché è fatto così" senza leggere il codice a freddo. Come il resto della documentazione dell'Engine, questo file si aggiorna dal template al merge: non è tuo, non lo adatti al progetto.

Se un file non compare qui né nei due README, è quasi sempre perché ha uno scopo singolo e il nome più il commento in testa bastano (es. `services/formatter.ts`, `services/validation.ts`): una voce dedicata non serve.

## Frontend — `frontend/src/app/core/engine/`

### Pipeline SSR (`server/`)

Il Node SSR (`server.ts`) è composto da moduli a scopo singolo, ciascuno leggibile a sé:

| File | Cosa fa | Perché è fatto così |
| :--- | :--- | :--- |
| `server-env.ts` | Sorgente unica delle variabili d'ambiente, valutata **lazy** | L'import non legge nessuna env var: il build Angular (route extraction) importa questo modulo senza che le variabili runtime esistano ancora. La validazione delle obbligatorie scatta in `server.ts`, all'avvio reale |
| `server-paths.ts` | Risolve le cartelle fisiche (dist browser/server, cache immagini) | La cache sta fuori da `src/assets` e isolata per progetto (hash del percorso): `ng serve` non ricarica la pagina a ogni miniatura generata e più progetti sullo stesso host non mischiano le immagini |
| `security-headers.ts` | Carica `security-headers.json` (sorgente condivisa col backend), ne verifica lo sha256 e applica gli header alle risposte Node | Un file del template modificato a mano ferma l'avvio: le estensioni passano da `security-headers.override.json`. Se il file manca, un fallback scritto nel codice tiene il server protetto invece di servire senza header |
| `asset-mapping.ts` / `asset-handler.ts` | Risolvono l'ID asset dichiarato in `mapping.json` al file fisico reale; riconoscono se un file è un'immagine raster ridimensionabile da Sharp | Nascondono i percorsi fisici e distinguono i formati compatibili col resize da quelli da servire tali e quali (es. SVG) |
| `image-cache.ts` | Cache su disco delle immagini ridimensionate, con tetto di dimensione (default 500 MB, `IMAGE_CACHE_MAX_MB`) e sweep LRU periodico (ogni 6h) | Evita di rigenerare ogni resize a ogni accesso senza lasciare che la cache cresca senza limite tra un deploy e l'altro |
| `fs-utils.ts` | `fileExists()`: verifica asincrona (`access`), non `existsSync` | Un check sincrono sospenderebbe l'event loop mentre il disco risponde; l'asincrono no |
| `preview-crypto.server.ts` | Cifra (AES-GCM) il payload di `/cdn-cgi/preview` | Vive in Node, mai nel bundle browser; la chiave, in ordine di fallback, è un secret esplicito → la prima API key → `nomeApp:versione`: il blob resta non falsificabile anche senza configurare nulla |
| `server-font-metrics.ts` + `preview-builder.ts` | Leggono le larghezze dei caratteri dai font reali (TTF, OTF, WOFF, WOFF2; cmap formato 4 o 12) per ogni `SystemFont` installato nel container e ogni font custom del catalogo (`font.principale`, `font.aggiuntivi`), e costruiscono l'SVG dell'og:image misurando il testo nello stesso font che lo disegna, compreso quello di `og.testo` | Tabelle scritte a mano andrebbero fuori allineamento a ogni cambio dei pacchetti font nel Dockerfile, e un testo misurato con un font e disegnato con un altro esce dal badge. Le regole di misura stanno in `services/font-metrics.ts`: testo in NFC; caratteri invisibili (zero-width, marcatori di direzione, BOM, selettori di variante, accenti combinanti isolati) a zero; un carattere fuori tabella vale la sua lettera base (`ǎ` come `a`) o, senza, un em pieno, così nel dubbio il testo va a capo invece di uscire. Grassetto dal rapporto reale con la faccia 700 dichiarata in `faces`, altrimenti stima del grassetto sintetico di fontconfig; il regular viene dalla faccia più vicina a 400 in stile normale. Decompressione WOFF/WOFF2 con tetto a 32 MB. Metriche e nome letto da `fc-scan` si calcolano una volta per processo: un file sostituito in `fonts/` vuole un riavvio. Un font illeggibile ripiega sulle tabelle integrate (Liberation per un font custom) con una riga nel log |
| `routes/api-proxy.ts`, `routes/cdn-asset.ts`, `routes/og-preview.ts` | Handler Express concreti dietro `/api`, `/cdn-cgi/asset`, `/cdn-cgi/preview` | Le tre route sono descritte ad alto livello nel [README root](README.md) («Route SSR speciali»); qui c'è il "come" per chi deve toccarne il comportamento |

La guardia di deriva configurazione (`scripts/config/config-fingerprint.ts`, `scripts/config/settings-merge.ts`) funziona così: `config-fingerprint.ts` calcola un hash SHA1 (12 caratteri) delle sezioni identity-critiche di `global-settings.json` (`project`, `Localization`, `site`, `Features`; mai `.local.json`, che porta segreti). `generate-statics.ts` lo scrive in `environment.ts` come `configFingerprint` a ogni build; `server.ts` lo ricalcola a runtime dal config letto da `getBr1Settings()` e confronta i due valori al boot, con un warning se divergono: il server si accorge di essere partito con un `environment.ts` non rigenerato (tipico: `ng serve` lanciato senza `predev`/`prestart`, o `global-settings.json` modificato senza rilanciare la build). L'impronta non copre `site.ts`. `settings-merge.ts` (`deepMergeSettings`) è il merge profondo di `global-settings.local.json` sopra il base, con la stessa semantica di `scripts/lib/br1-config.sh`, condiviso fra `server-env.ts` (lettura runtime) e `generate-statics.ts` (lettura al build nel percorso file-based; l'ARG Docker `BR1_PROJECT_JSON` resta di proposito il file base, senza segreti). Un'unica implementazione: le due letture non divergono nella semantica di fusione.

Per `Features` c'è in più un controllo bloccante: `scripts/config/features.ts` lo legge in modo rigido al build (`readFeaturesStrict`) e come lo legge .NET all'avvio SSR (`readFeaturesLikeBackend`); se il valore compilato e quello montato non coincidono, il server esce con codice 1. Il controllo gira quando `server.mjs` è il processo principale; `ng serve` non lo esegue.

### Navigazione multilivello (`components/navbar`, `footer-nav*`, `nav-*`)

`navbar.component.ts`, `footer-nav.component.ts` + `footer-nav-group.component.ts` (footer, ricorsivo), `nav-dropdown.component.ts` + `nav-submenu.component.ts` (flyout desktop / accordion mobile della navbar) e l'atomo `nav-link.component.ts` sono la resa concreta della feature "Menu Multilivello" (descritta a livello di configurazione in `nav.ts` e nel root README): la scomposizione in più componenti gestisce la ricorsione dei gruppi annidati senza duplicare la logica di stato attivo/hover tra footer e navbar. `back-to-top.component.ts` è indipendente dal menu: la soglia di scroll viene da `aspetto.fab.tornaSuSoglia`, tradotta in pixel da `BACK_TO_TOP_SOGLIA_PX` (`design-system-presets.ts`).

Il raggio d'angolo e l'ombra di `.dropdown-menu`/`.context-menu` (desktop) e la durata delle loro animazioni leggono `--elevazioneRaggio`/`--shadowElevated`/`--movimentoPannello` invece di un letterale: sono le leve statiche del tema compilato (sezione più sotto). Il raggio del pannello mobile a foglio (`.context-menu-sheet`) resta fisso: convenzione del pattern bottom-sheet, non un'identità di design system.

`breakpoints.ts` espone `isDesktopViewport()`, letto da `navbar.component.ts` e `nav-submenu.component.ts`: legge la custom property CSS `--bp-md` (iniettata in `_base.scss` da `lib.$bp-md`) invece di duplicare `768px` in TS, sorgente unica del breakpoint desktop/mobile fra SCSS e TS. Sempre in `navbar.component.ts`, oltre al limite di annidamento (`NAV_DEPTH_WARN`/`NAV_DEPTH_MAX`, in `frontend/README.md`), c'è un limite indipendente sul numero di voci di primo livello: oltre `MAX_RECOMMENDED_TOP_LEVEL_ITEMS` (6) le voci in eccesso confluiscono in un dropdown finale "Altro", sintetico, non dichiarato in `site.ts`, con lo stesso rendering di un `addGroup`. La soglia coincide con quella del warning in console: chi corregge l'avviso in dev fa sparire anche l'overflow. La misura passa da `ResizeObserver` sulla larghezza reale disponibile, su desktop (su mobile lo stack verticale non ha overflow).

### Effetto smoke (`components/smoke-effect/smoke-effect.component.ts`)

Il componente che disegna l'animazione di particelle su `<canvas>`, montato da `app.component.ts` (la shell, tua) che gli passa `showSmoke` già calcolato. Il contratto che un design system scrive (`SmokePreset`, `intensita`, i default) sta in `frontend/README.md`, capitolo «Design system e tema» → Effetto smoke; qui come quella scelta diventa i numeri grezzi che il componente consuma.

`SMOKE_INTENSITY` (`design-system-presets.ts`) mappa ogni `SmokeIntensity` in `{ maximumVelocity, particleRadius, density }`; `risolviAspetto()` legge `smoke.intensita` (default `'pulviscolo'`) e produce la `SmokeSettings` risolta di `SiteConfig.aspetto.smoke`. I tre numeri non sono esposti perché `maximumVelocity` viene scalato per `0.02` dentro `initParticles()` (componente) prima di diventare velocità in px/frame: un fattore interno che nessun design system deve conoscere per scegliere un valore sensato, da qui i tre gradi nominati.

### Leve nominate del design system: risoluzione (`design-system-presets.ts`, `services/appearance.service.ts`)

Il "cosa" (nomi dei campi, valori, quando usare quale) è in `frontend/README.md`, capitolo «Design system e tema». Qui il "come": ogni leva è un'unione letterale (`'foglio'`/`'scatto'`/`'standard'`/ecc.), mai un numero grezzo nel contratto pubblico. La traduzione in valori concreti (float, stringhe CSS, classi Bootstrap) è un dettaglio interno, con una tabella `Record<Leva, Valore>` per leva in `design-system-presets.ts` (`MOVIMENTO_DURATA`, `ELEVAZIONE_TIERS`, `PULSAZIONE_TIERS`, `CONTENT_WIDTH_CLASSES`, `BREADCRUMB_SEPARATORE`, `BACK_TO_TOP_SOGLIA_PX`) che nessun design system importa. `risolviAspetto()` applica i default e produce `config.aspetto`: un vocabolario unico dal design system ai componenti.

**`colori.superfici` → palette (`AppearanceService.computePalette`).** `aspetto.colori.vividezza` (0/0.5/1) interpola in OKLCH la lucentezza (L) di ogni superficie di contenuto verso quella del colore che le governa (`liftBg()`): un'interpolazione lineare, non un valore letterale, perché preserva l'ordine relativo fra le superfici (base, surface, hover…) qualunque sia il grado scelto. Lo scarto fra il default-L di ogni superficie e quello della base (`surfacesAt`) si applica prima di `liftBg()`. Il boost di chroma delle superfici (×16 con un `colori.sfondo` esplicito) cresce con la vividezza, da ×1 a ×16. Il `secondary` calcolato ha chroma 0.75× quello del brand, tetto 0.12; un secondario diverso si dichiara in `colori.palette.secondary`.

`computePalette` calcola le cinque superfici di un tono insieme (`readableSurfaces`): se nemmeno nero o bianco reggono su tutte, dimezza lo scarto fra le superfici fino a farle coincidere con la base. Tutti i primi piani (testo, titoli, link, muted, primary come testo, secondario derivato, bordo) passano da `keepOnSurfaces`/`findContrastOnSurfaces`/`findCompliantColor`, tarati su tutte le superfici del tono e liberi di scavalcarle (più chiari in light, più scuri in dark) quando la vividezza le porta sulla loro stessa lucentezza; un colore che regge già resta com'è. Il bordo (≥3:1, WCAG 1.4.11) resta fuori dallo scarto delle superfici, ancorato al suo minimo. Il testo navbar si tara sullo sfondo navbar (≥4.5:1); il bordo navbar è decorativo. Costo di `'tenue'`/`'fusione'`: i margini di contrasto fra superfici si stringono, e un paio di primi piani derivati dal brand ripiegano su nero o bianco, senza violare WCAG. Unico limite fisico, segnalato in dev: superfici a luminanza media dove né nero né bianco arrivano al target. Un colore di `colori.palette` (`secondary`, `info` o un nome nuovo) non ha questo paracadute come fill: resta l'hex scelto; come testo usa la variante leggibile.

**Leve per-componente**, ognuna un lookup diretto da `ContestoSito.config.aspetto` a una classe o un valore, senza calcoli: `larghezza` (`app.component.ts`, classe sulla colonna breadcrumb/pannello; senza pannello il contenuto sta a tutta colonna e la leva non ha effetto), `breadcrumb.stile` (`breadcrumb.component.ts`, carattere separatore), `fab.cookie` (`cookie-banner.component.ts`, classe modificatrice `.cookie-reopen-btn--standard`; il lato resta `inset-inline-start`, opposto a `back-to-top`, in entrambi gli stili: cambiarlo raddoppierebbe la probabilità di sovrapporsi a un controllo di pagina), `badgeNotifiche` (`notification-bell.component.ts`, testo del badge svuotato + classe `--dot`), `pulsazione` (`.pulse-live` in `_utilities.scss`, via le leve statiche del tema compilato).

### Tema compilato (`scripts/build/theme-scss.ts`, `styles/engine/bootstrap.scss`)

- **Ingresso unico, la build.** `colorTema` (`global-settings.json`) e il design system (`site.ts`) sono fissi per l'intero deployment, e il punto in cui arrivano insieme è la build. `generate-statics.ts` (pre-hook di `start`, `start:docker`, `dev`, `build` e `watch`; il Dockerfile passa da `npm run build` con `BR1_PROJECT_JSON`) chiama `computePalette` con gli override di `siteOverrides()`, la stessa fonte di client, SSR e `og-preview.ts`, e `buildThemeScss` scrive `styles/engine/generated/_theme.scss` (gitignored). Il file contiene dati Sass e nessun CSS: i colori per tono (`$theme-light`, `$theme-dark`), i colori di palette (`$theme-custom`, `$theme-accents`), la polarità (`$theme-polarity`), le leve statiche (`$theme-static`: movimento, elevazione, pulsazione, raggio della lightbox, stack del font) e le `@font-face` del design system (`$theme-font-faces`). `angular.json` carica `bootstrap.scss` come primo foglio di stile.
- **File assente.** Sass si ferma sulla riga dell'import, che nel commento nomina `npm run generate:statics`: `ng serve` lanciato a mano va preceduto da quel comando. Gli script di test (`tsc-check.sh`, `theme-check.sh`) lo eseguono da sé; in CI la generazione precede lint, tipi e test.
- **Contratto TS↔Sass.** Ogni lettura di `_theme.scss` passa da `lib.required()` (`base/_lib.scss`): una chiave mancante ferma la compilazione con un errore che la nomina, invece di tornare `null` e lasciar ricadere `$primary` sul blu di Bootstrap.
- **Chi calcola cosa.** L'Engine calcola gli input che Bootstrap si aspetta già validi (primary, link, testo, titoli, superfici, bordo, navbar), tarati WCAG sulle superfici reali; `bootstrap.scss` li passa come variabili (`$primary`, `$body-bg`/`$body-bg-dark`, `$link-color`/`$link-color-dark`…), fissa le percentuali di hover/active dei bottoni (12/16/18/22%) e compila Bootstrap da sorgente, che deriva il resto: subtle/emphasis, hover/active, testo sopra i fill con `color-contrast()`, focus, stati attivi. Per questo `bootstrap` in `package.json` è fissato a `~5.3.x`: la compilazione da sorgente dipende dai nomi interni di Bootstrap.
- **Cosa resta scritto a mano.** I token che Bootstrap non ha (superfici, navbar, primary come testo) in un blocco per `[data-bs-theme]` (mixin `engine-tone-tokens`); le variabili che seguono il tono via `var()` dove Bootstrap non fa calcoli colore (`$component-active-bg`, barra di progresso, anello di focus); i colori di tema che cambiano fra i due toni, resi custom property per tono (mixin `tone-color-vars`, stesse funzioni di `_buttons.scss`), così un sottoalbero con il suo `data-bs-theme` eredita i valori del proprio tono.
- **Per tono, oltre ai colori.** `--bs-focus-ring-color` è ridichiarata in ogni blocco, perché Bootstrap la dichiara su `:root` e il suo `var()` interno si risolverebbe una volta col link chiaro. Le immagini SVG di spunta, radio, trattino dell'indeterminato e switch sono compilate per tono (mixin `tone-form-images`, custom property `--tone-form-*`): un `var()` non entra in un data URI. L'alone del cursore del range usa il fondo del tono.
- **Polarità.** `$theme-polarity` porta, per tono, il modo reale del fondo (dalla luminanza di `body-bg`). Con superfici vivide il tono scuro di un brand chiaro ha fondo chiaro: `bootstrap.scss` sceglie allora le derivazioni del modo del fondo (bordo traslucido, hover dei link, colori di form e componenti, mappe subtle/emphasis) e il `color-scheme` corrispondente.
- **Pavimento dell'emphasis.** Le derivazioni di Bootstrap sono percentuali fisse, senza verifica di contrasto. `_readable-emphasis` sposta ogni `*-text-emphasis` a passi di `shade-color`/`tint-color` finché regge 4.5:1 sul suo subtle e sulle cinque superfici del tono; se dieci passi non bastano prova nero e bianco; se neanche quelli bastano, la build emette un `@warn` con colore e tono.
- **Runtime.** Nessun CSS di colore iniettato. `theme-init.js` imposta `data-bs-theme` su `<html>` dalla preferenza dell'OS prima del primo paint, `AppearanceService` lo aggiorna se la preferenza cambia, l'SSR scrive il tono iniziale e i `<meta name="theme-color">`. `computePalette` resta lato TS per chi disegna fuori dal CSS (canvas, QR, og:image, manifest).
- **Stampa** (`base/_print.scss`). `:root` e ogni `[data-bs-theme]` rimettono testo, titoli, link e superfici a nero su bianco: un pannello o una card scuri non stampano testo chiaro su carta bianca. Accenti, emphasis e bordi restano quelli del tono.
- **Compilato all'avvio.** Cambiare design system o `colorTema` con il dev server acceso non aggiorna i colori: riavvio di `npm run dev` o `npm run generate:statics`. `AppearanceService` (QR, og:image) calcola già la palette nuova, il CSS no.

### Overlay del menu contestuale (`components/context-menu/`)

`context-menu-overlay.component.ts` (rendering dell'overlay) e `context-menu.models.ts` (forma di `ContextMenuOption`) sono l'implementazione dietro il selettore `[appContextMenu]`. Posizionamento, portal e dismiss-on-outside-click sono CDK Overlay/Portal (`context-menu.directive.ts`); la navigazione da tastiera fra le voci usa CDK `FocusKeyManager` (`@angular/cdk/a11y`) invece di un roving-focus scritto a mano, stessa libreria, nessuna dipendenza aggiuntiva. Il `.cdk-overlay-container` sta fuori dal pannello: menu, lightbox e dropdown montati lì prendono il tono della pagina, non quello del pannello da cui partono.

### Notifiche/dialog (`services/notification.service.ts`) — SweetAlert2, non Bootstrap JS: valutato e scartato

`NotificationService` (alert/confirm/choose/prompt/toast/promise) resta su SweetAlert2, non su `bootstrap.Modal`/`bootstrap.Toast`: una scelta valutata, non un'inerzia. SweetAlert2 dà gratis quattro cose che un port perderebbe o dovrebbe riscrivere a mano: un'API a Promise (Bootstrap è a eventi, `shown.bs.modal`/`hidden.bs.toast`), le icone built-in (successo/errore/warning/info/domanda, assenti in Bootstrap), un primitivo per l'input-dialog validato di `prompt()` (assente in Bootstrap), il pause-on-hover/focus con barra di progresso del toast (per WCAG 2.2.1; nessuna delle due librerie lo dà gratis). Il costo del bundle è pari (~31KB gzip SweetAlert2 contro ~24KB gzip il JS di Bootstrap, che l'Engine non importa). L'unico vantaggio di un port sarebbe il theming (il DOM nativo Bootstrap eredita `data-bs-theme` da sé, mentre ogni chiamata ricostruisce `Swal.mixin({theme: ..., customClass: {...}})` da `AppearanceService.themeTone()`, e i colori del popup vengono dal ponte `--swal2-*` → token del tema in `_bootstrap-theme.scss`): non basta a giustificare la riscrittura di ~10 metodi pubblici con perdita di funzionalità. Coerente col principio guida dell'Engine ("usa il meccanismo nativo se il framework lo offre già"): qui il framework non offre l'equivalente, per questo è un NO deliberato e non un'eccezione alla regola.

### CSP: `style-src-attr 'unsafe-inline'` — deliberato, non un gap dimenticato

`security-headers.json` (`Content-Security-Policy`) lascia `style-src-attr 'self' 'unsafe-inline'` mentre `script-src`/`style-src-elem` usano un nonce per risposta. Due motivi indipendenti, oltre all'integrazione di librerie terze (Mapbox GL JS ne è l'esempio più comune: scrive posizioni calcolate a runtime come attributi `style=""` inline): (1) CSP non offre un meccanismo a nonce/hash praticabile per gli attributi di stile inline, e l'alternativa `'unsafe-hashes'` pretende il valore esatto della stringa in anticipo, impossibile per stili calcolati a runtime; (2) ogni binding `[style.qualcosa]` nei template Angular, durante l'SSR, esce come attributo `style=""` letterale nell'HTML (lato server non c'è CSSOM), e quel markup iniziale è soggetto a `style-src-attr`: senza `'unsafe-inline'` ogni pagina con un binding `[style.x]` (diversi nell'Engine, es. `[style.height.px]`) avrebbe un flash di contenuto non stilizzato fino all'idratazione. `extendCsp` (`csp.ts`) resta il punto giusto per estendere `script-src`/`connect-src`/`frame-src` ecc. con domini esterni (YouTube, Mapbox, altri) via `security-headers.override.json`; è `style-src-attr` a non doversi stringere.

### Direttive di rendering dichiarativo (`directives/`)

`img-render.directive.ts` e `qr-render.directive.ts` sono l'implementazione dietro `[appImgRender]`/`[appQrContent]` (selettori documentati in `frontend/README.md`): trasformano un `<img>` nel render di un'immagine generata via `ImgBuilderService` o di un QR via `QrCodeService`.

### Interceptor errori API (`interceptors/api-error.interceptor.ts`)

Implementa il toast automatico sugli errori HTTP delle chiamate non marcate `{ silent: true }`. È un interceptor Angular a sé, fuori da `BaseApiService`, per tenere puro il client API (idioma Angular per i concern trasversali).

### Cookie interni (`services/cookie/`)

`cookie-type.ts` definisce `ConsentCategory` (Technical/Analytics/Profiling/TechnicalOptional), la tassonomia dietro le voci di `COOKIE_MAP` (vedi ricetta in `AGENTS.md`). Technical è l'unica esente da consenso per legge (strettamente necessaria, mai uno switch nel banner); TechnicalOptional è il suo contrario, tecnica ma non indispensabile (es. il Service Worker/PWA built-in), trattata come Analytics/Profiling: proprio switch, proprio consenso. `cookie-utils.ts` è un check statico che `siteBuilder.ts` esegue in fase di build per decidere se il sito ha una Cookie Policy (`resolveLegalPages`): non è runtime, è un dettaglio di composizione del sito.

### Connessione realtime, dettaglio interno (`services/notification-connection.ts`)

Tiene il `connectionId` corrente in un signal separato da `NotificationStreamService`: `BaseApiService` lo legge (per l'header `X-Connection-Id`) senza iniettare, e senza attivare, lo stream. Finché nessuno attiva lo stream resta `null`.

### Pagine legali (`legal/`, `pages/policy/`, `pages/content.resolver.ts`)

La sezione `legal` di `site.ts` (`LegalDefinition`) ha uno slot per pagina standard, valorizzato con un `PageType` del progetto, come `homePage`/`loginPage`. La semantica sta nello slot: la tabella `STANDARD` gli associa rotta, chiavi i18n e cartella Markdown. `resolveLegalPages` produce la lista delle pagine attive (gli slot valorizzati, la Cookie Policy se `hasCookiesConfigured`, poi `extra`) e fallisce se il sito usa cookie senza lo slot `cookie`. Su quella lista lavorano `filterManagedLegalPages` (override: una pagina dichiarata a mano in `pages` vince), `buildPolicySection` (rotte, con `role: 'legal'` e fuori indice di serie) e `getLegalPage` (Markdown e data).

`SiteConfig.cookiePolicy` è derivato: è il `PageType` dello slot `cookie` se la pagina esiste, altrimenti `null`. Banner e `PolicyComponent` lo leggono per riconoscerla.

Ogni voce di `STANDARD` porta una ricetta (`LegalRecipe`): le parti per funzione da cercare nella cartella, se mostrare l'elenco cookie, lo stato di accessibilità e i dati di navigazione, e quale sezione identità chiude la pagina. `activeLegalPartials` calcola quali parti sono accese da `Features` e `COOKIE_MAP`; la usano sia `ContentResolver.loadLegal` (carica `intro`, `outro` e per ogni parte la sua cartella o la variante `off/`) sia `checkLegalFolders` al build (`scripts/build/legal-check.ts`, che controlla anche che ogni cartella di parte presente abbia tutte le lingue servite): runtime e controllo non divergono. Una pagina con `markdown` (slot sostitutivo o `extra`) salta la composizione: `loadLegal` legge `<markdown>.<lingua>.md` e della ricetta resta solo l'elenco cookie, che `PolicyComponent` rende dopo il testo. La sezione identità è `LegalRecipe.identity` (titolo + `FooterField[]`), risolta da `resolveFooterFields` in `PolicyComponent`; lo stato di accessibilità è `recipe.accessibilityStatus`, reso da `AccessibilityStatementComponent`.

Il layout è una cartella per pagina, una sottocartella per parte e un file per lingua (`<pagina>/<parte>/<lingua>.md`, variante a funzione spenta in `<parte>/off/<lingua>.md`). Caricamento: `generate-statics.ts` scrive in `environment.legalFiles` quali parti esistono per pagina, e `loadLegal` chiede quelle e nessun'altra, così un facoltativo assente (un `outro`, una variante `off/`) non genera traffico. Nell'SSR del build servito il testo si legge da disco (`dist/browser/assets/legal`, lettore registrato in `app.config.server.ts`) e viaggia nella pagina in `TransferState` (chiave `legal:<file>`, consumata una volta), così l'idratazione non lo riscarica; se la cartella del build non esiste (`ng serve`) passa da HTTP come nel browser. Conseguenza: un file aggiunto dopo l'ultimo `generate:statics` resta invisibile fino al riavvio. `checkLegalFolders` guarda le cartelle delle pagine composte e i file `markdown` delle pagine dichiarate; il resto di `assets/legal/` è del progetto. Il titolare del trattamento (nome, recapito) non è un controllo di build: `identitySection` in `PolicyComponent` lo risolve a runtime da `GET /identity`, e senza dati la sezione semplicemente non compare — nessuno script del frontend può saperlo in anticipo, l'identità può arrivare da un `IIdentityStore` qualsiasi, non solo dal file.

Dati di navigazione (`legal/hosting-info.ts`): `loadHostingInfo` in `server/server-env.ts` legge il file di `HOSTING_INFO_PATH` (il compose lo monta) o di `frontend.hostingInfo`, e `parseHostingInfo` lo valida; `server.ts` lo legge all'avvio, così un file indicato ma assente o non valido ferma il processo e uno non indicato lascia un avviso nel log. `computeLegalFacts()` (stessa fonte, `server-env.ts`) costruisce `LEGAL_FACTS` (installazione, URL del sito, finestra del rate limiting da `getBr1Settings()`, già ridotti a ciò che il testo usa: limite spento = `null`, finestra dei login solo col login acceso): `app.config.server.ts` lo mette in `TransferState` (`br1_legal_facts`) a ogni pagina renderizzata dal server, e la stessa funzione alimenta `/internal/legal-facts` (`server.ts` + `routes/legal-facts.ts`), l'endpoint che il browser interroga di scorta quando `TransferState` non li ha mai avuti (prima pagina della sessione senza SSR, `requiresAuth`). `app.config.ts` rilegge `TransferState` nel browser; `PolicyComponent` ci prova, e se è `null` chiama l'endpoint una sola volta, prima di passare i fatti a `renderNavigationData`, che produce il Markdown dalle chiavi `nav*`: con un fatto assente la sua frase non c'è, e senza file restano l'elenco dei dati tipico e il criterio di conservazione.

### Fogli base (`styles/engine/base/`)

Regole globali dietro comportamenti che i README danno per scontati. Il perché di quelle meno ovvie:

- **Vista full-bleed** (`_layout.scss`, `.fit-viewport`): `<main>` diventa colonna flex e la pagina ne eredita l'altezza. `!important` sull'host perché una utility `.d-*` di Bootstrap (anch'essa `!important`) spezzerebbe la catena lasciando il contenuto ad altezza 0; `width: 100%` perché in una colonna flex una pagina tutta in `position: absolute` (mappe, canvas) collassa a larghezza 0.
- **Host di pagina `display: block`** (`_layout.scss`): i custom element nascono inline. La regola è dentro `:where()`, a specificità minima, così un `:host` o una utility `d-*` della pagina vince senza `!important`.
- **`overflow-x: clip`, non `hidden`** (`_utilities.scss`, sotto `md`): `hidden` su un asse rende scrollabile anche l'altro e taglierebbe i dropdown della navbar.
- **Focus da tastiera** (`_base.scss`): anello su `:focus-visible`; il reset al click/tap sta in `:where()`, così non batte gli stati di focus dei componenti.
- **Altezza in `dvh`** (`_base.scss`, `html` e `app-root`): su mobile segue le barre del browser, e le viste full-bleed misurano l'altezza visibile; `100vh` resta come ripiego.
- **`.surface-elevated` neutra**: gli overlay usano lo sfondo pagina, non il brand, riservato alle CTA.
- **`.icon-fixed`** (`_a11y.scss`): i glifi Font Awesome hanno larghezze diverse, e senza un box fisso un bottone-icona che cambia stato cambia misura.
- **Stampa, navbar nascosta con `app-navbar.d-block`** (`_print.scss`): la classe host `.d-block` è `!important` e batterebbe il selettore di tag nudo.

### Editor Markdown (`components/markdown-editor/`)

- **Due strati nella stessa cella di griglia**: sotto un `<pre>` col testo colorato, sopra la textarea vera con testo trasparente. Stessa metrica per entrambi, e gli stili dei token cambiano colore e decorazioni, mai la larghezza dei caratteri: il cursore cade sempre sul carattere colorato. L'altezza la dà il `<pre>`, niente scroll da sincronizzare.
- **Colori dal lexer della pipeline** (`markdown-editor-text.ts`, `highlightMarkdown`, sopra `MarkdownPipe.lex()`): ogni token è ritrovato nel sorgente col suo `raw` e il testo fra i token passa com'è, così l'output contiene tutto il testo, nello stesso ordine. Dove marked normalizza un `raw` (blockquote su più righe, voce di elenco con continuazione) si prova coi figli. I `\r\n` si uniformano come fa la textarea. Link e immagini passano dalla stessa regola di sicurezza URL della pipe (`pipes/markdown-url-safety.ts`): un link con URL non sicuro non si colora come link, un'immagine non sicura esce barrata come l'HTML grezzo scartato. Nelle citazioni si attenua il marcatore `>`, non il testo.
- **Cronologia propria**: i comandi della barra riscrivono la textarea via codice, e una riscrittura via codice svuota l'annulla del browser. Annulla/Ripeti (anche da tastiera e da menu contestuale, via `beforeinput`) usano una pila dell'editor. Si annulla una parola alla volta: battute della stessa specie a meno di un secondo l'una dall'altra (`TYPING_GROUP_MS`) formano un passo, e lo spazio resta con la parola precedente. Incolla, taglia, trascina, correzioni ortografiche e comandi della barra fanno sempre un passo a sé. Tetti: 200 passi (`HISTORY_LIMIT`) e 2 milioni di caratteri in tutto (`HISTORY_MAX_CHARS`, ogni passo tiene il testo intero); oltre, si scartano i passi più vecchi.
- **`mousedown` senza default sui bottoni**: il clic non toglie focus e selezione alla textarea.

### Scelte di `generate-statics.ts`

- **`/theme-init.js` con path assoluto**: lo `<script>` sta prima di `<base href>`, un path relativo darebbe 404 sulle pagine annidate.
- **Blocco PWA fra marker nudi** (`PWA:START`/`PWA:END`): rigenerato per intero, pieno con `isWebApp`, vuoto altrimenti; nell'HTML servito non finiscono path di build né nomi di flag.
- **Lingue**: anche un `SupportedLanguages: []` o tutto malformato ricade sulla lingua di default, perché zero lingue vorrebbe dire zero rotte, senza errore.
- **Tema e testi legali**: scrive `_theme.scss` (sezione «Tema compilato») e `environment.legalFiles` (sezione «Pagine legali»), ed esegue `legal-check` e la lettura rigida di `Features`: un errore lì ferma il build prima di Angular.
- **`.local` di sviluppo** (`scripts/config/local-settings.ts`): con `global-settings.json` nella root del repository e nessun `global-settings.local.json`, lo scrive con API key e `SecretKey` generate, come `setup.mjs`; il backend fa lo stesso in Development (`Engine/LocalSettingsFile.cs`). In Docker il file base non sta nella root del repository (arriva da `BR1_PROJECT_JSON`), quindi non scatta.
- **Palette degenerata** (`paletteDegenerata` in `scripts/build/theme-scss.ts`): la palette si calcola una volta per build; se le cinque superfici di un tono coincidono, il build si ferma con brand e superfici nel messaggio, perché da lì testo, link e fill del primario finirebbero tutti sul nero o sul bianco. Gli altri ripieghi di contrasto del motore colore (un `console.warn` per token) escono in una riga aggregata. `site.colorTema` è validato prima del calcolo: un valore non esadecimale darebbe `#NaNNaNNaN` in `_theme.scss`.

### Budget bundle iniziale (`angular.json`, `maximumWarning: 930kB`)

Il valore traccia il peso EAGER dell'Engine (shell + navbar/footer/cookie-banner/smoke-effect/back-to-top/breadcrumb, Bootstrap CSS, router/forms) a schermo pulito, senza margine per le pagine e i componenti che un progetto figlio aggiungerà. È deliberato: un figlio che monta qualcosa di eager (un widget sempre visibile, un init globale, una libreria di stato) e fa scattare il warning non ha rotto un limite dell'Engine, ha superato il peso di partenza, e alza lui `maximumWarning`/`maximumError` nel proprio `angular.json`, consapevolmente, nello stesso commit che aggiunge il peso. Stesso principio delle estensioni additive di `security-headers.override.json`: la base resta stretta apposta, l'allargamento è un'azione esplicita e visibile in diff, mai un default permissivo che nasconde una regressione (un budget largo abbastanza da non disturbare nessuno è il modo in cui un warning finisce ignorato). Quando l'Engine stesso si avvicina al tetto, la causa va diagnosticata e risolta con lo stesso approccio (import statico → dinamico dove il grafo lo permette), non alzando il numero.
